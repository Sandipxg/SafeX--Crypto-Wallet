# Chapter 3.1 — Core Blockchain Architecture (Ethereum Internals)

> **Objective**: Understand Ethereum's internal mechanics at a protocol level so that creating, signing, and broadcasting raw EVM transactions becomes a deterministic process.

---

# 1. The Core Architecture: Two Databases

Ethereum relies on two fundamental data structures operating concurrently:

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                    BLOCKCHAIN (Immutable History)                       │
│                                                                         │
│  [ Block #1 ] ──► [ Block #2 ] ──► [ Block #3 ] ──► ... ──► [ Block #N ]│
│  (Stores every block, header, transaction, and receipt forever)         │
└─────────────────────────────────────────────────────────────────────────┘
                                     │
                                     │ State Transition (Execution)
                                     ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                     WORLD STATE (Current Snapshot)                      │
│                                                                         │
│  Address 0x71C7... ──► Balance: 5.2 ETH  | Nonce: 4                    │
│  Address 0x3B9a... ──► Balance: 12.0 ETH | Nonce: 12                   │
│  Contract 0xA0b8...──► CodeHash & Contract Storage State                │
└─────────────────────────────────────────────────────────────────────────┘
```

| Database | Purpose | Key Characteristic |
| :--- | :--- | :--- |
| **Blockchain** | Appended log storing every block and transaction | Immutable, append-only historical record |
| **World State** | Key-value store mapping addresses to current account state | Dynamic snapshot updated with every block |

---

# 2. The Git Analogy

| Git Concept | Ethereum Blockchain Concept |
| :--- | :--- |
| **Commit** | **Block** |
| **Git History (`git log`)** | **Blockchain History** |
| **Current Working Directory (`checkout`)** | **World State** |

- Every block is like a Git commit containing state changes.
- The World State represents the current checkout of the repository.

---

# 3. What is a Block?

A block consists of two distinct components: **Header** and **Body**.

```text
┌─────────────────────────────────────────────────────────────────────────┐
│                              BLOCK                                      │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │                          BLOCK HEADER                             │  │
│  │  Parent Hash  |  Block Number  |  Timestamp  |  Gas Limit/Used    │  │
│  │  State Root   |  Tx Root       |  Receipts Root  |  Base Fee      │  │
│  └───────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐  │
│  │                          BLOCK BODY                               │  │
│  │  [ Transaction #1, Transaction #2, Transaction #3 ... Tx #N ]     │  │
│  └───────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────┘
```

| Component | Contents |
| :--- | :--- |
| **Block Header** | Metadata, cryptographic Merkle roots, timestamps, gas tracking |
| **Block Body** | Ordered list of transactions included in the block |

---

# 4. Block Header Fields (Ethereum's DNA)

| Header Field | Type / Size | Purpose |
| :--- | :--- | :--- |
| `parentHash` | 32-byte Hash | Keccak-256 hash of the previous block header (creates chain continuity) |
| `number` | Integer | Height of the block in the chain (Genesis = 0) |
| `timestamp` | Unix Timestamp | Seconds elapsed since Unix epoch when validator produced block |
| `gasLimit` | BigInt | Maximum total gas allowed to be consumed by all transactions in this block |
| `gasUsed` | BigInt | Actual total gas consumed by all executed transactions in this block |
| `stateRoot` | 32-byte Hash | Merkle Patricia Trie root hash of the World State after executing all transactions |
| `transactionsRoot` | 32-byte Hash | Merkle tree root hash of all transactions in the block body |
| `receiptsRoot` | 32-byte Hash | Merkle tree root hash of execution receipts generated by transactions |
| `baseFeePerGas` | BigInt | Minimum gas fee rate (in wei) required per gas unit; burned by the protocol |

---

# 5. Parent Hash & Chain Immutability

Each block header explicitly stores the 32-byte `parentHash` of the preceding block:

```text
[ Block #1 ]                   [ Block #2 ]                   [ Block #3 ]
Hash: 0xA1B2                   Hash: 0xC3D4                   Hash: 0xE5F6
                               Parent: 0xA1B2                 Parent: 0xC3D4
```

- If an attacker tampers with a historical transaction in **Block #1**:
  1. The block header hash of Block #1 changes to `0xXXXX`.
  2. Block #2's `parentHash` field (`0xA1B2`) no longer matches `0xXXXX`.
  3. Block #2 and every subsequent block in the chain become invalid.

---

# 6. Block Body (Transactions)

The block body contains an array of raw transactions:

```json
[
  "0x02f87201808459682f00...",
  "0x02f87001018459682f00...",
  "0x02f87301028459682f00..."
]
```

- A block does **not** store balances directly. It stores transaction instructions.
- Balances are updated in the **World State** when validators execute the block body.

---

# 7. What is a Transaction Object?

An EIP-1559 transaction object contains the following standard fields:

| Field | Meaning |
| :--- | :--- |
| `from` | Sender's Ethereum address (`0x...`) |
| `to` | Recipient address or target smart contract address |
| `value` | Amount of ETH to transfer (denominated in wei) |
| `nonce` | Sequential counter tracking number of transactions sent by sender |
| `gasLimit` | Maximum gas units sender authorizes for transaction execution |
| `maxFeePerGas` | Absolute maximum total fee (Base Fee + Priority Fee) sender agrees to pay per gas |
| `maxPriorityFeePerGas` | Tip per gas unit paid directly to the block validator |
| `chainId` | Network identifier (e.g. `1` for Ethereum Mainnet, `11155111` for Sepolia Testnet) |
| `data` | Binary payload (empty `0x` for plain ETH transfer; ABI call bytes for smart contracts) |
| `signature` | ECDSA signature components ($v, r, s$) proving sender owns the private key |

---

# 8. Transaction Serialization (Why Bytes Matter)

JSON is human-readable application formatting:

```json
{
  "to": "0x71C7656EC7ab88b098def1734b743b44628b36d2",
  "value": "1000000000000000000"
}
```

The Ethereum network receives **raw binary byte streams**:

```text
0x02f87201808459682f008459682f008252089471c7656ec7ab88b098def1734b743b44628b36d2880de0b6b3a764000080c0
```

- **Serialization** converts structured objects into deterministic byte arrays.
- Ethereum uses **RLP (Recursive Length Prefix)** encoding to serialize fields into deterministic binary payloads before hashing and signing.

---

# 9. State Transition Engine

Ethereum is defined as a deterministic **transaction-based state machine**:

$$\text{WorldState}_{N+1} = \text{APPLY}(\text{WorldState}_N, \text{Block}_{N+1})$$

```text
[ Old World State ] ───► + [ Executed Block Transactions ] ───► [ New World State ]
(Alice: 5 ETH)             (Alice sends 1 ETH to Bob)            (Alice: 4 ETH)
(Bob:   2 ETH)                                                   (Bob:   3 ETH)
```

- Every transaction transforms the World State.
- Once executed, the validator computes the cryptographic root hash of the new World State.

---

# 10. State Root (The World's Fingerprint)

The `stateRoot` is a single 32-byte Keccak-256 hash representing the entire World State at a given block height.

```text
World State Accounts
├── 0x71C7... (Balance, Nonce, Storage)
├── 0x3B9a... (Balance, Nonce, Storage) ──► Merkle Patricia Trie ──► State Root Hash
└── 0xA0b8... (Balance, Nonce, Storage)                             (0x9d4a...)
```

- If an attacker attempts to alter a single account balance in the database, the root hash of the Merkle Patricia Trie changes completely.
- Peers reject any block proposal where the calculated state root does not match the header's `stateRoot`.

---

# 11. Transactions Root & Merkle Trees

Transactions inside a block are organized into a **Merkle Tree**:

```text
                    Transactions Root Hash
                              │
               ┌──────────────┴──────────────┐
            Hash 12                       Hash 34
         ┌─────┴─────┐                 ┌─────┴─────┐
       Hash 1      Hash 2            Hash 3      Hash 4
         │           │                 │           │
       Tx 1        Tx 2              Tx 3        Tx 4
```

- **Merkle Proofs**: Allows light clients to verify that a specific transaction `Tx 3` is included in a block without downloading the entire block body.

---

# 12. Receipts Root

When a transaction executes, the EVM generates a **Transaction Receipt**:

| Receipt Field | Purpose |
| :--- | :--- |
| `status` | `1` (Success) or `0` (Reverted/Failed) |
| `cumulativeGasUsed` | Total gas consumed in the block up to this transaction |
| `logs` | Event logs emitted by smart contracts during execution |
| `contractAddress` | Deployed contract address (if transaction created a contract) |

All receipts in a block are Merkle-tree hashed to produce the `receiptsRoot` in the header.

---

# 13. Gas Limit vs. Gas Used

| Term | Scope | Defined By |
| :--- | :--- | :--- |
| **Block `gasLimit`** | Maximum gas allowed for an entire block | Set by protocol consensus (~30,000,000 gas) |
| **Block `gasUsed`** | Actual gas consumed by all transactions in the block | Calculated by EVM execution |
| **Transaction `gasLimit`** | Maximum gas units authorized for one transaction | Set by sender (e.g. 21,000 for standard ETH transfer) |
| **Transaction `gasUsed`** | Actual gas consumed by one transaction | Calculated by EVM execution (e.g. 21,000) |

- Unused gas is refunded to the sender's account.

---

# 14. Base Fee & Priority Fee (EIP-1559)

Under EIP-1559:

$$\text{Total Gas Price} = \text{baseFeePerGas} + \text{maxPriorityFeePerGas}$$

$$\text{Total Transaction Fee} = \text{Gas Used} \times (\text{baseFeePerGas} + \text{maxPriorityFeePerGas})$$

- **Base Fee**: Dynamically adjusted by protocol block demand; **burned permanently**.
- **Priority Fee (Tip)**: Set by user; paid directly to the validator as an incentive for inclusion.

---

# 15. Block Verification Workflow by Validators

```text
Incoming Proposed Block
          │
          ├── 1. Verify Parent Hash (Chain Continuity)
          ├── 2. Verify Block Timestamp & Gas Limit Boundaries
          ├── 3. Verify ECDSA Signatures for all Transactions
          ├── 4. Execute Transactions in EVM (Update Nonces & Balances)
          ├── 5. Compute State Root, Tx Root & Receipts Root
          │
          ▼
   Does Calculated State Root == Header State Root?
   ├── YES ──► Accept Block & Broadcast Attestation
   └── NO  ──► Reject Block (Invalid State Transition)
```

# 🎯 Concept Revision Cheat Sheet

| Question | Core Engineering Answer |
| :--- | :--- |
| **Why doesn't a block store user balances?** | Blocks store state transitions (transactions). Current balances live in the World State database. |
| **Difference between Blockchain & World State?** | Blockchain = immutable history log. World State = current snapshot of account balances and nonces. |
| **Why store `stateRoot` in block header?** | Provides a single 32-byte cryptographic fingerprint verifying the entire World State without storing state data in the header. |
| **Why serialize transactions into RLP bytes?** | Network protocols require deterministic binary payloads to compute hashes and verify ECDSA signatures consistently. |
| **If 1 transaction changes in a block, which hashes change?** | `transactionsRoot`, `stateRoot`, `receiptsRoot`, and the Block Header Hash. |

# Chapter 3.2 — Ethereum Account Model & Nonces

> **Objective**: Master the 4 fields of an Ethereum Account State, the critical role of Nonces in preventing replay attacks, and how nonces are managed across client wallets and mempools.

---

# 1. What is an Ethereum Account?

Ethereum is an **account-based system**. The World State acts as a key-value store mapping 20-byte addresses to their current **Account State**:

```text
World State Database (Key-Value Store):
Map < EthereumAddress (0x...), AccountState >
```

---

# 2. The Account State Object (4 Fields)

Every single address on Ethereum points to an **Account State** object containing 4 fields:

```typescript
interface AccountState {
  nonce: bigint        // Transaction counter
  balance: bigint      // ETH balance stored in Wei (integer)
  storageRoot: string  // 32-byte Merkle Patricia Trie root for contract storage
  codeHash: string     // 32-byte Keccak-256 hash of smart contract bytecode
}
```

---

# 3. Balance (Stored in Wei)

- Ethereum **never stores floating-point decimals**.
- All account balances are stored as 256-bit unsigned integer **Wei**:

$$1 \text{ ETH} = 10^{18} \text{ Wei} = 1,000,000,000,000,000,000 \text{ Wei}$$

- SafeX UI converts Wei $\rightarrow$ ETH for display, while backend services always handle exact integer Wei.

---

# 4. What is a Nonce?

> **Nonce Definition**: A sequential counter recording the number of **outgoing transactions initiated** by an account.

```text
Timeline:
[ Account Created ] ──► Nonce = 0
  ├── Send Tx #0   ──► Nonce = 1
  ├── Send Tx #1   ──► Nonce = 2
  └── Send Tx #2   ──► Nonce = 3
```

- A brand new address starts with `nonce = 0`.
- Every executed transaction initiated by that account increments its nonce by **+1**.

---

# 5. Incoming vs. Outgoing Transactions

| Action | Sender Nonce | Receiver Nonce |
| :--- | :--- | :--- |
| **Alice sends 1 ETH to Bob** | ✅ **Alice Nonce +1** | ❌ **Bob Nonce Unchanged** |
| **Bob receives 1 ETH** | ❌ Unchanged | ❌ Unchanged |

> 🔑 **Golden Rule**: Nonce only tracks **outgoing** transactions initiated by the account. Receiving ETH or tokens never increments your nonce.

---

# 6. Why Does Nonce Exist? (Preventing Replay Attacks)

Without nonces, Ethereum would be vulnerable to **Replay Attacks** and **Double Spending**:

### 🚨 Replay Attack Vulnerability (Without Nonce):
1. Alice signs a transaction: *"Send 1 ETH to Bob"*.
2. An attacker intercepts the signed transaction bytes.
3. The attacker re-broadcasts the exact same signed transaction 100 times.
4. Without nonces, the network would execute it 100 times, draining 100 ETH from Alice!

### 🛡️ How Nonces Prevent Replays:
Every transaction explicitly includes the sender's current nonce:

```json
{
  "nonce": 7,
  "from": "0xAlice...",
  "to": "0xBob...",
  "value": "1000000000000000000"
}
```

1. Alice sends transaction with `nonce = 7`.
2. Ethereum executes it, and updates Alice's account state to `nonce = 8`.
3. If an attacker re-broadcasts the signed transaction (`nonce = 7`), the network compares incoming `nonce = 7` with state `nonce = 8`.
4. The node rejects it immediately with `nonce too low`! Replay attack blocked.

---

# 7. Strict Sequential Nonce Execution Order

Ethereum validators execute transactions from an account in **strict sequential order**:

$$\text{Nonce } 15 \longrightarrow \text{Nonce } 16 \longrightarrow \text{Nonce } 17$$

- If Alice submits Tx15, Tx16, and Tx17, the protocol **guarantees** Tx15 executes before Tx16, and Tx16 executes before Tx17.

---

# 8. What Happens if a Nonce Gap Occurs? (Nonce Too High)

Suppose Alice's current confirmed nonce is `5`.
Alice submits a transaction with `nonce = 8`.

```text
Current Confirmed Nonce: 5

Mempool Queue:
  ├── Tx (Nonce 6) ──► MISSING 🛑
  ├── Tx (Nonce 7) ──► MISSING 🛑
  └── Tx (Nonce 8) ──► Status: WAITING IN MEMPOOL QUEUE
```

- **Ethereum Response**: The node does **not** fail the transaction; it places Tx8 in the mempool **pending queue**.
- Tx8 sits waiting until Tx6 and Tx7 arrive and execute first.

---

# 9. What Happens if Nonce is Too Low?

Suppose Alice's current confirmed nonce is `5`.
Alice submits a transaction with `nonce = 3`.

- **Ethereum Response**: The node rejects the transaction immediately with the RPC error:
  `"nonce too low"`

---

# 10. Pending Nonce vs. Confirmed Nonce

| Nonce State | RPC Parameter | Scope | Description |
| :--- | :--- | :--- | :--- |
| **Confirmed Nonce** | `"latest"` | Blockchain State | Number of transactions already confirmed in mined blocks |
| **Pending Nonce** | `"pending"` | Mempool State | Confirmed count + pending unmined transactions in mempool |

```text
Blockchain Confirmed Nonce = 10
  ├── Pending Tx #1 (Nonce 10) in Mempool
  ├── Pending Tx #2 (Nonce 11) in Mempool
  └── Next Available Nonce = 12
```

- Wallets MUST query `"pending"` when constructing new transactions to avoid duplicate nonce collisions!

---

# 11. EOA (Externally Owned Account) vs. Smart Contract Account

| Feature | EOA (Externally Owned Account) | Smart Contract Account |
| :--- | :--- | :--- |
| **Controlled By** | Private Key (via secp256k1) | Deployed EVM Bytecode |
| **Initiate Txs?** | ✅ YES (Can originate transactions) | ❌ NO (Only executes when called) |
| **`codeHash`** | `0xc5d24601...` (Keccak-256 hash of empty string) | Keccak-256 hash of contract bytecode |
| **`storageRoot`** | `0x56e81f17...` (Hash of empty storage trie) | Merkle Patricia Trie root of contract storage |

- **SafeX User Wallets** are EOAs.

---

# 12. Replacing & Speeding Up Pending Transactions

If a user's transaction with `nonce = 10` is stuck pending due to low gas fees:

```text
Original Pending Tx:  [ Nonce: 10, MaxFee: 20 Gwei ] ──► Stuck in Mempool

Speed Up / Cancel:   [ Nonce: 10, MaxFee: 30 Gwei ] ──► Broadcasted to Mempool
```

1. **Speed Up**: Broadcast a new transaction with the **SAME NONCE** (`10`) and recipient, but with a **$\ge 10\%$ higher gas fee**. Validators drop the old underpriced transaction and include the new one.
2. **Cancel**: Broadcast a transaction with the **SAME NONCE** (`10`), value = `0 ETH`, sent to **YOURSELF**, with a higher gas fee. Once mined, it consumes nonce `10` and cancels the stuck transaction.

---

# 13. Common Nonce RPC Errors

| Error Message | Cause | Resolution |
| :--- | :--- | :--- |
| `nonce too low` | Transaction nonce has already been mined | Re-fetch pending nonce using `eth_getTransactionCount(addr, "pending")` |
| `replacement transaction underpriced` | Replacing pending nonce without raising fee by $\ge 10\%$ | Increase `maxPriorityFeePerGas` and `maxFeePerGas` by at least 10–12% |
| `already known` | Identical signed transaction bytes already exist in mempool | Wait for confirmation or speed up with higher fee |

---

# 🎯 Concept Revision Cheat Sheet

| Question | Core Engineering Answer |
| :--- | :--- |
| **Why does receiving ETH not change nonce?** | Nonces count outgoing transactions initiated by an account. |
| **Why can't Ethereum execute Nonce 12 before Nonce 11?** | Execution order determines state changes deterministically; changing order alters state outcomes. |
| **Why query `"pending"` instead of `"latest"`?** | `"latest"` ignores unmined mempool transactions, causing duplicate nonce collisions. |
| **How does Speed Up work in wallets?** | Re-broadcasts a transaction using the **same nonce** with a higher gas fee tip. |
| **What is an EOA state vs Smart Contract state?** | EOA has empty `codeHash` and `storageRoot`. Smart contract has bytecode `codeHash` and storage trie `storageRoot`. |

# Chapter 3.3 — Transaction Lifecycle (Wallet → Mempool → Validator → Block)

> **Objective**: Trace the complete 12-stage end-to-end lifecycle of an EVM transaction from user UI interaction to cryptographic execution, mempool propagation, block inclusion, and receipt confirmation.

---

# 1. The 12-Stage End-to-End Pipeline Overview

```text
 1. User Taps SEND ─────────►  2. Build Tx Object ─────────►  3. Local ECDSA Sign
                                                                    │
                                                                    ▼
 6. Node Validation ◄────────  5. JSON-RPC Broadcast ◄──────  4. Raw Bytes Created
         │
         ▼
 7. Enters Mempool ─────────►  8. Peer Propagation ────────►  9. Validator Selects
                                                                    │
                                                                    ▼
12. UI Confirmed ◄────────── 11. World State Updated ◄────── 10. EVM Execution
```

---

# 2. Stage 1: User Taps "Send" in Client UI

The user selects parameters on the frontend:

| Field | Example Value |
| :--- | :--- |
| **Recipient (`to`)** | `0xBob...` |
| **Amount (`value`)** | `1.0 ETH` |
| **Target Network** | Sepolia Testnet (`chainId: 11155111`) |

---

# 3. Stage 2: SafeX Builds Unsigned Transaction Object

SafeX constructs an unsigned EIP-1559 JSON object:

```typescript
const unsignedTx = {
  chainId: 11155111n,             // Sepolia Testnet
  nonce: 8n,                      // Fetched via eth_getTransactionCount(addr, "pending")
  to: "0xBobAddress...",
  value: 1000000000000000000n,    // 1 ETH converted to Wei (10^18)
  gasLimit: 21000n,               // Estimated via eth_estimateGas
  maxFeePerGas: 35000000000n,     // 35 Gwei max fee
  maxPriorityFeePerGas: 2000000000n, // 2 Gwei validator tip
  data: "0x"                      // Empty hex string for native ETH transfer
}
```

- At this stage, the transaction object contains **no signature** and **no sender `from` field**.

---

# 4. Stage 3: Local Offline ECDSA Signing

The client wallet signs the transaction hash using the user's decrypted private key in memory:

```text
[ Private Key (RAM) ] + [ Transaction Hash ] ──► [ ECDSA Algorithm ] ──► Signature (r, s, v)
```

- **Non-Custodial Security**: The private key **never leaves local client RAM**.
- The ECDSA signature ($r, s, v$) mathematically proves ownership without revealing the key.

---

# 5. Stage 4: Raw RLP Serialization

The transaction object and signature are serialized into a **Raw RLP Byte String**:

```text
0x02f8728301b207808459682f008459682f008252089471c7656ec7ab88b098def1734b743b44628b36d2880de0b6b3a764000080c0...
```

- **Why Raw Bytes?**: Network protocols exchange deterministic binary byte streams rather than JSON.

---

# 6. Stage 5: JSON-RPC Broadcast

SafeX submits the raw byte payload to an Ethereum RPC node (Infura, Alchemy, or custom Geth node):

```json
{
  "jsonrpc": "2.0",
  "method": "eth_sendRawTransaction",
  "params": [
    "0x02f8728301b20780..."
  ],
  "id": 1
}
```

---

# 7. Stage 6: Ethereum RPC Node Validation Checklist

Before accepting the raw transaction into its mempool, the node performs strict checks:

| Validation Step | Rejection Reason if Invalid |
| :--- | :--- |
| **Signature Check** | `invalid signature` (Sender address derived via `ecrecover`) |
| **Nonce Check** | `nonce too low` (Must match current pending nonce) |
| **Balance Check** | `insufficient funds` (Balance must cover `value + gasLimit * maxFeePerGas`) |
| **Gas Limit Check** | `gas limit exceeded` (Must meet standard 21,000 unit minimum) |
| **Chain ID Check** | `invalid chain id` (Prevents Sepolia tx replay on Mainnet) |

---

# 8. Stage 7 & 8: The Mempool & Peer Propagation

Once validated, the transaction enters the **Mempool** (Memory Pool):

```text
[ Node A Mempool ] ───► Gossip Protocol ───► [ Node B Mempool ] ───► [ Node C Mempool ]
```

- **Temporary Waiting Room**: The mempool holds unconfirmed transactions waiting to be picked by a block builder/validator.
- **P2P Propagation**: Transactions propagate across Ethereum nodes via a peer-to-peer gossip protocol. Each node maintains its own local mempool.

---

# 9. Stage 9: Validator Transaction Selection (Gas Pricing)

Validators build blocks by selecting transactions from the mempool, sorting primarily by **`maxPriorityFeePerGas` (Tip)**:

| Transaction | Sender | Priority Fee (Tip) | Selection Priority |
| :--- | :--- | :--- | :--- |
| Tx #1 | Eve | 10 Gwei | 🥇 **1st (Highest Tip)** |
| Tx #2 | Charlie | 5 Gwei | 🥈 **2nd** |
| Tx #3 | Alice (SafeX) | 2 Gwei | 🥉 **3rd** |
| Tx #4 | Dave | 1 Gwei | 4th (Lowest Tip) |

- **Block Capacity**: Block size is constrained by the block `gasLimit` (~30,000,000 gas units $\approx$ 1,400 simple transfers per block).

---

# 10. Stage 10: EVM Execution Workflow

When executing Alice's transaction in a block, the validator runs the EVM:

```text
1. Load Alice's Account State from World State
2. Derive Sender Address from ECDSA Signature
3. Verify Nonce == 8
4. Deduct (value + maxGasFee) from Alice's Balance
5. Add value (1 ETH) to Bob's Balance
6. Increment Alice's Nonce (8 ──► 9)
7. Burn Base Fee | Pay Priority Fee Tip to Validator
8. Generate Execution Receipt (status: 0x1, gasUsed: 21000)
```

---

# 11. Stage 11 & 12: New World State, Block Broadcast & Consensus

1. The validator computes the new Merkle Patricia Trie root hash (**`stateRoot`**).
2. The validator seals the block header and broadcasts the new block to the network.
3. Attesting nodes re-run the execution; if their calculated `stateRoot` matches, the block is appended to the blockchain.

---

# 12. Stage 13 & 14: Immediate Transaction Hash Generation

The moment `eth_sendRawTransaction` succeeds, the RPC node immediately returns the **Transaction Hash**:

$$\text{Tx Hash} = \text{Keccak256}(\text{Raw Transaction Bytes})$$

- The Tx Hash is computed deterministically from the byte stream **before** the transaction is included in a mined block.
- SafeX uses this Tx Hash to display the transaction in the UI with a pending status and an Etherscan explorer link.

---

# 13. Stage 15 & 16: Receipt Polling (`eth_getTransactionReceipt`)

Client wallets periodically poll the RPC endpoint until a **Transaction Receipt** is generated:

```json
{
  "method": "eth_getTransactionReceipt",
  "params": ["0x7fa8d9..."]
}
```

### Receipt Data Structure:

| Field | Meaning / Usage |
| :--- | :--- |
| `status` | `0x1` (Success) or `0x0` (Reverted / Failed) |
| `blockNumber` | Height of the block in which the transaction was mined |
| `gasUsed` | Exact gas units consumed during execution (e.g. `21000`) |
| `effectiveGasPrice` | Actual total fee paid per gas unit |
| `logs` | Event logs emitted (used for ERC20 transfer tracking) |

---

# 14. Stage 17 & 18: Confirmations & Chain Reorg Protection

$$\text{Confirmations} = (\text{Current Block Height} - \text{Mined Block Height}) + 1$$

| Confirmations | Network Trust Level |
| :--- | :--- |
| **0 Confirmations** | Pending in Mempool (Unconfirmed) |
| **1 Confirmation** | Included in latest mined block |
| **12+ Confirmations** | Considered finalized (Protected against chain reorganizations) |

# 🎯 Concept Revision Cheat Sheet

| Question | Core Engineering Answer |
| :--- | :--- |
| **Why validate before mempool?** | Prevents invalid or un-fundable spam transactions from clogging network peer bandwidth. |
| **Why are mempools different across nodes?** | Transactions propagate peer-to-peer over time; nodes see transactions in slightly different order. |
| **Why is Tx Hash returned immediately?** | Tx Hash is simply `Keccak256(rawBytes)`, which is calculated before mining. |
| **What changes in World State after execution?** | Sender balance decreases, recipient balance increases, sender nonce increments by +1. |
| **Why poll `eth_getTransactionReceipt`?** | Broadcasting to mempool does not guarantee execution; receipt confirms block inclusion and execution status. |
